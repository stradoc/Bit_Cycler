# CLAUDE.md

**Bit Cycler**: CSC 3501 (Computer Organization) team project. A browser tycoon + rhythm game where each beat is one CPU clock cycle: the player is the CPU's control unit, routing each instruction to its unit on the beat, stalling for hazards and guessing branches, and earns money from contracts to buy the hardware that does those jobs for them. Due by pull request on Nov 30, 2026.

Stack: Phaser 3.90, TypeScript compiled with plain `tsc` (no bundler), raw Web Audio API, `node:test`, npm for dev tools only. The game ships from `game/` (copied to `games/bit-cycler/` in the course repo at submission).

Instruction set: RISC-V inspired. The CPU chip's word size grows 8 → 16 → 32 → 64-bit as shop upgrades, in the order features reached real microprocessors, and it sets the era (green CRT, DOS, 90s desktop, modern terminal). An era is the look of its period's computers, not a claim that word size changes the screen. In the CPU model, word size is the width of a contract's data (8-, 16-, 32- or 64-bit numbers, offered once your chip is that wide): the same loops with `lh` / `lw` / `ld` and `sh` / `sw` / `sd`, registers as wide as the data, and a footprint that fills the caches faster (`ROADMAP.md` item 2).

**Layers.** `sim/`, `rhythm/`, `data/`, `format.ts`, `saveFile.ts`, `song/setup.ts`, `song/words.ts`, `song/results.ts` and `visual/asciiChart.ts` never use Phaser or the browser at runtime, so `tests/` runs them in Node. Put rules and numbers there and test them; drawing and sound go in `scenes/`, `ui/`, `visual/`, `audio/` and the other `song/` parts.

**One place per thing.** An era is described only in `ui/eras.ts`; code asks `era.kind`, `era.screen.*`, `era.computer.*`, `era.sound.*`, never "is this era 2". Sizes and positions come from `ui/theme.ts`. Sounds are played only by name (`this.cue('move')`), and animations too (`motionOf(this).play('glide-in', targets)`; the song screen is all on it, and a test keeps it so; the other screens are being moved: `ROADMAP.md` item 0). Prices and balance numbers live only in `data/economy.ts`. The CPU is put into words only by `cpuName` / `cpuLine` (word size: `bitsName`), and a chip is found by its width only with `chipByBits` (`sim/progress.ts`). A screen that must be redrawn when the era changes (a new chip, another save) asks `eraChanged()` (`ui/screen.ts`). Text the song screen shows lives only in `song/words.ts`. What the guide says lives in `data/tours.ts` (tours) and `song/words.ts` (practice's tips); only `ui/guide.ts` draws it.

**One way to do each thing (binding, from the team).** Keep the code modular, reusable and standardized: every kind of job has one implementation, and new features are built from it.
- **Reuse before writing.** Before adding anything, look for the piece that already does it and use it. The shared pieces: screens (`Screen`: header, hints, the pause menu), lists (`ListMenu`), boxes and panels (`Box`, `panel`), TICK (`Guide`: tours, held lines, questions), sounds (cues by name), character drawings (`visual/asciiChart.ts`: bars and `stackedBar`, `frame`, `center`, `spread`, `monthGrid`, the calendar page, the timecard, in plain ASCII or code page 437 (`Glyphs`); block letters and digits: `banner` and `blockPixels` in `data/menuFiles.ts`), cards (a stamp, rows of text and bars, keys: a `Card`, drawn the era's way by `drawCard` in `ui/card.ts`), pixel art (`data/pixelArt.ts`, drawn by `drawPixels`), the calendar (`sim/workday.ts`: dates from day 1 = Monday, November 1, time left, whether a job fits today, finishing a job, ending the day, the day history, and `eventsOn`: one list of what's marked on each day, so a new kind of event is added there and the calendar screen shows it; clock and hours in `format.ts`), 3D models (the renderer in `visual/model3d.ts`: a model is a list of non-overlapping boxes with a `Look` for its materials, drawn by `ModelView`; the chip and the title are built that way), animations (recipes in `data/motions.ts`, played by `motionOf`, looked at in the motion lab), a song's setup (`songSetup`), waits that freeze the song (`Pipeline.waitLeft`, drawn over `waitBeats`), numbers (`data/economy.ts`), words (`song/words.ts`, `data/tours.ts`), formatting (`format.ts`), saving (`save.ts`, cleaned by `saveFile.ts`).
- **Extend, don't copy.** If the piece is almost right, give it an option or a parameter rather than writing a second version. What's been done this way: the deep pipeline's refill reuses the memory wait; the settings take `returnTo` instead of a second settings screen; `ListMenu` took `depth` and `heading`; TICK's questions reuse his bubble.
- **One concept, one home.** A new idea (the workday's clock, reputation, a trophy) gets one module that owns its state, rules and wording, with a small documented interface. Other code calls that interface; it never works the idea out again or reaches into another part's private fields.
- **Data over branches.** Variants are entries in a table (eras in `ERAS`, lessons in `LESSONS`, tutorial levels in `TUTORIAL`, shop items in `shopItems`), not `if` chains spread across files. Adding a variant should mean adding an entry.
- **Rules apart from drawing.** What a feature does (state, numbers, decisions) goes in the pure layers and is tested; how it looks goes in `scenes/`, `ui/`, `visual/`. A screen should only ask and draw.
- **Replace, don't pile up.** When something new replaces something old, delete the old (code, compiled files, docs, tests), as the briefing screen was. No second path kept "just in case".
- **Three times means stop.** If the same logic is about to appear in a third place, make it one function first. Before committing, search for near-copies of what was added and merge them.
- **Record the shared pieces.** A new reusable piece goes in the code map above and, if it's a new kind of thing to add, in "Adding things" below.

## Adding things

**A screen.**
1. Make `scenes/NameScene.ts` extending `Screen` (`super('name')`). In `create()`, call `this.setUp()` first (options: `hum: false` for screens with their own music, `glow: 'menu'` for dark screens, `windowed: false` before the program "starts").
2. Build it from the kit: `this.header(title, subtitle)`, `this.corner(money)`, `this.aboutLine()`, `this.messageLine()`, `this.hints('[ENTER] ...', '[Q] BACK')`, `this.text()` / `this.textAt()`, `new ListMenu(this, this.era, {...})`, `new Box(...)`, `panel(...)`, `PressButton.create(...)`.
3. Handle keys in `protected onKey(key)`: return `true` when handled (`M` toggles the hum otherwise). Use `this.cue(...)` for sounds and `this.back(scene, data)` to leave. A screen in the game (not one of the main menu's) gives Esc / Q a pause menu instead: return its rows from `pauseItems()` (`this.places()` gives the board, shop, settings and main menu; `this.go(...)` makes another), say `[Q] MENU` in the hints (Q, not Esc: Esc works too, but Vimium-style extensions swallow it, so the game names Q), and stop anything that runs on its own in `onPause(open)`.
4. Register it in `main.ts`'s scene list, and give it its window title, terminal path and DOS menu item in `TITLES`, `PATHS` and `DOS_ITEM` (`visual/terminal.ts`).
5. Reach it from somewhere: the main menu's disk (`TitleScene.rootEntries`, named the era's way by `data/menuFiles.ts`), the board, or `flow.ts`.
6. Screenshot it in all four eras.

**A sound.**
- A short sound: add a recipe to `CUES` in `audio/cues.ts`, built from `audio/synth.ts` (`tone`, `flat`, `buzz`, `noiseBurst`, `blip`), into a bus: `bus(ctx, 'ui')` for the interface, `'song'` for the song. If it needs more than a time and a volume, declare its options in `Extras`. Add its folder in `CUE_FOLDER` (`audio/render.ts`; the compiler insists). Play it with `this.cue(name)`, or `cueOn(ctx, ...)` without a scene.
- Loudness: `LEVELS` in `audio/mix.ts`. A new kind of sound gets a new bus there rather than a hard-coded gain.
- A longer sound: follow `audio/machine.ts`: build it at a time on any context (`powerOnAt(ctx, era, t)`), with a small wrapper that plays it now in a scene. That's what lets `audio/render.ts` export it.
- A recording: add it to `assets/sounds/`, load it like `audio/samples.ts`, credit it in `assets/sounds/CREDITS.txt` and CREDITS.TXT (`data/menuFiles.ts`). A recording needs the user's approval first (rule 3).
- Then run `npm run export-sounds` and check its length, peak and pitch. Nobody can hear headless audio: tell the user what still needs a listen.

**An era, or a change to one.** Everything is one entry in `ERAS` (`ui/eras.ts`): the chip whose era it is (`bits`; the active save's chip picks the era, `?era=N` previews another for the session), colors, font, `kind` (how widgets draw: `terminal`, `dos`, `desktop`, `modern`), `screen` (resolution, smoothness, glow, CRT overlay, LCD grid, window or DOS bars), `computer` (CRT or LCD, drive, BIOS, file names, splash colors), `sound`, how its 3D models are drawn (`models`), how TICK is drawn (`tick`, a look in `TICK_LOOKS`), its charts' colors (`tones`), an optional `dark` variant. A new font is loaded in `loadFonts` (`visual/display.ts`) and credited. A new `kind` needs a case wherever `kind` is switched on (`ui/widgets.ts`, `ui/list.ts`, `song/highway.ts`, `KITS` in `ui/card.ts`); a new frame style needs `FRAMES` (`visual/display.ts`) and `drawChrome` (`visual/terminal.ts`). The boot and file-name tests run over every era.

**A card** (the results card; a timecard). Describe it as data, a `Card` (`visual/asciiChart.ts`), in a pure module: an optional stamp (a word and its `Tone`), rows (`line` with a `right` end, `gap`, `deadline`, `stack` of segments, `legend`; a row can name the `part` it's about), keys, and how wide its rows are in characters. Test it with `cardLines` (its lines in either character set, and each part's lines). Draw it with `drawCard(scene, era, card, at)` (`ui/card.ts`): one container to place or glide in, and where each part is (`areas`, for TICK's `where`). Each kind of era draws it its own way: in characters (ASCII; code page 437 in each tone's color), like a Windows 98 dialog, or flat and modern. Its colors are the era's `tones`. A new kind of row is a case in `cardLines` and `paintRow`, and in each `Painter` if it's drawn.

**A 3D model** (a trophy, say). Build it from boxes (`box`, `turnedBox` in `visual/model3d.ts`) that never overlap (touching is fine), give its materials a `Look` (full colors, brightness in the green era, EGA colors, where the light comes from), and draw it with a `ModelView` (its camera and the area it's drawn in), posed every frame it moves. Test that its boxes don't overlap and draw in order from every pose it's seen in (`tests/model3d.test.ts`). The shop's chip (`visual/chip3d.ts`) and the main menu's title (`visual/title3d.ts`) are the examples.

**TICK's look, or a new pose.** His poses and looks are data (`data/tick.ts`). A new variant of a part (a mouth, say) goes in every look: a string in each character sheet, rows in the pixel sheet, numbers for the vector one (`vectorPose`); `poseAt` says when he takes it (a new mood: `Mood`, then `poseAt`). A new look is an entry in `TICK_LOOKS`: a character sheet (lines with `{slots}` and each part's variants, every pose the same width; `accent` slots in the era's accent color), a pixel sheet (a palette, a base, the parts drawn over it), or a new kind drawn in `visual/tickFigure.ts`; an era names it in `tick`. His bob, walk and spotlight are recipes in `MOTIONS`. `tests/tick.test.ts` checks every pose in every look.

**A song.** An entry in `SONGS` (`data/songs.ts`), written like a tracker's pattern (the notation is at the top of that file): a chord a bar, 16 steps a bar for the bass, drums, arpeggio and melody, a drum fill for the last bar, and its sounds (pulse waves, a triangle, vibrato, an echo). `audio/music.ts` plays it, adding parts as the pipeline fills (bass and melody, then hats, drums, the arpeggio), and reacts to the run as `song/groove.ts` says; `songFor` gives each program its song. The tests read every song and keep each part in range (`tests/songs.test.ts`). Then `npm run export-sounds` writes it to `sound-export/music/` to listen to. A style for another era is a new set of songs and sounds there, as data.

**An animation.** A recipe in `MOTIONS` (`data/motions.ts`): its tracks (keyframes for x, y, alpha, scale, angle, or `progress`, how far along a path something is: plain values, `{ by }` offsets from where it starts, `{ times }` multiples of it, or `'goal'` toward a value it's given), its duration, easing, delay, stagger, and whether it loops (or yoyos); its `group` (`screen` unless given, `tick`, `song`); `essential` if the player needs to see it even with REDUCED MOTION (which makes the rest jump, and holds loops still). Play it with `motionOf(scene).play(name, targets, { goal, done, remove, beatMs, duration })` (`visual/motion.ts`; the screen drives it every frame on `performance.now()`; `remove` destroys the targets when it ends). Never branch on the era to animate: each era's way of moving is its `motion` in `ERAS` (`cut`, `step` with `fps` and a character `cell`, `tween`, `ease`; `afterglow` for the CRT), and an era that should play one recipe its own way gives it in `motion.variants`; a group that moves one way in every era is in `GROUP_STYLES` (TICK and the song: smooth everywhere, the user's choice). The tests run every recipe in every era (`tests/motions.test.ts`). Look at it in the motion lab (developer screen, MOTION LAB, or `?scene=motions`: every recipe on a sample, in any era with [E]; `&motion=note-flush&at=300` freezes one for a screenshot).
- **On the song screen** (a gameplay animation): a `song` recipe, lasting one of the lengths in `PACE` (a new length is a new entry there; the tests check). Something that has to fit in a beat says how much of one (`beats`) and is played with `beatMs` (the beat as played, replays' speed included); a length the game decides (a memory wait) is `duration`. The `song/` part that owns the thing plays it; where a falling note is stays on the beat in `Highway.syncNotes`, not in a recipe. Something with no position of its own (a value on the bus) is a plain object with a `progress` that the part draws from every frame (`Bus`); the camera is `viewOf(scene)`. Words it shows (a callout, a stamp) go in `song/words.ts`. No tweens, camera effects or hand-timed waves in `song/` or `PipelineScene` (a test fails on them).

**A gameplay feature in the song** (a new hazard, a key, a kind of note):
1. Model it in `sim/` (usually `pipeline.ts`, switched on by a `PipelineOptions` flag), with tests that match hand-worked cycle counts. Check the numbers against Patterson & Hennessy, and label anything approximate. The song gets the flag from `song/setup.ts`: add it to `SongStart` and `SongSetup`, work it out in `songSetup` (from the tier, the save, or a URL shortcut) and hand it to the simulator in `pipelineOptions`; retries and replays carry it on by themselves. Test it in `tests/songSetup.test.ts`.
2. Judge it in `rhythm/pipelineRun.ts` (a new `Action` or `Outcome`, what `CycleReport` tells the screen), with tests.
3. Show it: drawing in the `song/` part it belongs to, its animation a `song` recipe (see "An animation"), its feedback, practice tip (`Tip`, shown once and said by the guide, with the part of the screen it points at) and click-to-learn entry in `song/words.ts` (shared definitions in `data/glossary.ts`), what it adds to a run's report (`RunReport` in `song/results.ts`: on the card only if it's about the job's performance, otherwise in TICK's `resultsTour`), and the wiring in `PipelineScene` (`handleKey`, `showDecision`, `onCycle`). Sound through a cue.
4. Keep the design rules: no quizzes, a mistake costs cycles and never ends the song, practice explains instead of punishing, the RELAXED difficulty still works (`DIFFICULTIES` in `rhythm/tempo.ts`), and replays reproduce it (record what the player did in `recording` or `dialRecording`, which the replay gets as a `Recording` from `song/setup.ts`).

**A CPU tier or shop part.** A chip (a word size) goes in `CHIPS` (`data/economy.ts`: the tier it follows, its top clock step); a CPU part says which chip it needs (`bits`), and the shop lists chips and parts in that order. The tier goes in `data/tiers.ts` (its `TierOptions` reach the song through `songSetup` in `song/setup.ts`, which also reads the parts that change the song, like the L1, from the save). The part's price goes in `data/economy.ts`, and it goes on sale in `shopItems` / `buy` (`sim/progress.ts`, tested in `tests/progress.test.ts`). Its lesson goes in `data/lessons.ts` (its song setup; `practice: false` for an idea with no practice of its own) and as a tour of the song screen in `SONG_TOURS` (`data/tours.ts`, pictures in `visual/diagrams.ts`), played straight after buying via `teachAfterPurchase` (`flow.ts`): TICK's tour, then practice, then play. BRIEFS on the main menu lists it by itself. Draw it on the shop's chip (`buildChip` in `visual/chip3d.ts`), report it in the boot (`hardware` in `data/boot.ts`), and add it to the developer screen (`scenes/DevScene.ts`) and the cheats (`cheats.ts`). A part that's in the game but still being reworked gets `wip: true` (its shop name and its lesson in BRIEFS are marked WIP: `WIP_PARTS`, `wipLabel`, `isWip`); take it off when it's done. So the board deals jobs that show it off, give it an entry in `SHOWCASES` (`sim/showcase.ts`, under its shop key: when it's in use, the hardware without it, and if only some jobs show it, which kinds and widths); if no job shows it well, add a `showcase` kind to the generator. The same goes for an upgrade to the L1 and a cache level.

**An upgrade to the L1** (8 lines, 2-way sets, 8-byte blocks). An entry in `CACHE_UPGRADES` (`data/economy.ts`): the field of the cache's shape it changes and to what, its price and lesson. `cacheShape` (`sim/memory.ts`) builds the L1 from the ones owned (`Progress.cacheUpgrades`, cleaned in `saveFile.ts`), `cacheOf` gives the player's, and the shop sells it once the L1 is in. Everything that shows the cache reads the shape: the panel's box (a line a row while 4 fit, two columns for 8), the words (`song/words.ts`: line or set, the address split), the chip (`buildChip`), the boot. Its lesson (`data/lessons.ts`) runs its practice on the first L1 with only that upgrade (`options.l1`), on a program made for the misses it fixes (`data/programs.ts`), and holds up a picture of that program's loads before and after, worked out on the real caches (`loadsOn` in `visual/diagrams.ts`); the results compare it with the first L1 (`first-l1`).

**A cache level below the L1** (the L2, the L3). An entry in `LOWER_CACHES` (`sim/memory.ts`: its name, shape and lookup time) and in `MEMORY_PARTS` (`data/economy.ts`: price, the chip it needs, its lesson, what the shop says before then); `Progress.cacheLevels` counts the levels owned and `lowerCachesOf` the ones below the L1. It reaches the song as `SongSetup.lowerCaches` (`?cache=l2`) and the simulator as `PipelineOptions.lowerCaches`, and everything that names levels reads the table: the lookup line, the bus, the waits and the tips (`song/words.ts`), the results (where loads were found, the AMAT, the run without the last level), the boot, the developer screen. Give it a patch of the die in `LOWER_AREAS` (`visual/chip3d.ts`). Its lesson shows the levels (`ladder` in `visual/diagrams.ts`) and a program's loads before and after (`missRow` with levels), and practices on the first L1 with the levels up to it (`options.lowerCaches`).

**An optional part with a switch** (the deep pipeline). Its numbers go in `data/economy.ts` (`DEEP_PIPELINE`), the save keeps `'none' | 'off' | 'on'` (`Progress.deepPipeline`, cleaned in `saveFile.ts`), `deepActive` says when it's in use, `toggleDeep` switches it, and the shop lists it with `switchedOn` so Enter switches instead of buying. It reaches the song through `SongSetup.deep` (`song/setup.ts`) and the simulator through `PipelineOptions.wrongGuessCycles`: a wrong guess's extra cycles are a refill, a wait like a memory wait (`Pipeline.refillWait`, `refillCycles`; the run squeezes both into a few beats as `waitBeats`).

**A contract or program kind.** A new game's first job is the hand-written tutorial (`TUTORIAL_PROGRAM` in `data/programs.ts`, alone on the board: `newCampaign` and `fillBoard` in `sim/progress.ts`); if it changes, keep each core instruction before its loop repeats (`tests/tutorial.test.ts`), since lesson 1's close looks run on it. For the endless board, add the kind to `sim/generator.ts`: a builder (its source, register roles, key registers, memory note, answers) and an entry in `KERNELS` under its name, with its clients and job wording in `CLIENTS`. A builder takes a `Layout` (the data's width): every address is an item's place times its size (`L.at`), loads and stores are `L.load` / `L.store`, the pointer steps by `L.bytes`, data values come from `L.values` and results go through `L.wrap`, and it says "byte" as `L.noun`; a byte program must come out exactly as before (a seed rebuilds an old save's job). Numbers written in the program (an `addi`) stay small at any width. Never rename or remove a kind: a contract stores only its program's name ("SUM #4821", "32-BIT SUM #4821"), and `programByName` rebuilds it as the kind and width the name says (`kindOf`, `bitsOf`), so old saves keep their jobs. Which widths the board offers, and what each pays, is `DATA_WIDTHS` (`data/economy.ts`; `dataWidth` in `sim/progress.ts`). A loop longer than 7 lines won't fit the job sheet. A kind made only to show off a part (an unrolled loop) is marked `showcase` in `KERNELS`: it's never drawn at random, so the seeds' draw stays as it was, and `SHOWCASES` names it under its part. The tests run thousands of seeds checking answers, memory bounds and key registers. Contract sizes (each grade's share of its deadline on your CPU), deadlines, the workday, offer lengths and pay are in `data/economy.ts` (`WORKDAY`, `GRADES`, `PAY`); `newContract` sizes a job from your CPU's speed on its own program.

**Campaign mode** (planned: a debt to pay off by a far deadline, with the endless board as free play after). Not started; settle the open questions in `ROADMAP.md` with the user first (what missing the deadline does, installments, how fast time passes). The pieces fit like this:
- State: new fields in `Progress` (`sim/progress.ts`) with their new-game values in `NEW_GAME`. Old saves get those values and range-checks in `cleanProgress` (`saveFile.ts`); test both in `tests/save.test.ts`.
- Time: the workday's calendar is built (`sim/workday.ts`): a finished job moves the clock on by its time as played (`finishJob`, from `jobSeconds` in `song/results.ts`; `contractSeconds` in `sim/progress.ts` is the board's estimate), and logging off ends the day (`endDay`). A campaign's deadline counts those days.
- Showing it: the board's header and corner (`BoardScene`), the results card (`song/results.ts`), the boot's report (`data/boot.ts`), and the save slots (`SavesScene`).
- The end: a new screen (see above), started from `flow.ts` or the board when the debt is paid or the deadline passes. NEWGAME.EXE (`TitleScene`) starts a campaign; free play needs its own entry.
- Numbers go in `data/economy.ts`; add developer-screen rows and cheats to jump to any point.

**A lesson, a tour, or a click-to-learn entry.** There are no slides: every lesson is TICK on the real screen.
- A tour is the guide (TICK, a robot drawn the era's way: `data/tick.ts`) walking the player through a real screen, step by step: each step says one short sentence-case line and points at a part of the screen (the rest dims) or holds up a picture (a `DiagramId`), and may give his `mood` (happy, cheer, worried; calm otherwise). The steps go in `data/tours.ts`, with the names of the parts they may point at as a type (`BoardTarget`, `SongTarget`); the screen says where those parts are (`where(target)` in `BoardScene` and `PipelineScene`), makes a `Guide` (`ui/guide.ts`), calls `guide.tour(steps, where, done)`, sends it Enter (`guide.next()`, not a held-down key's repeats) while `guide.waiting`, and calls `guide.update(now)` every frame. Enter first shows the rest of the words, then closes them; nothing can be skipped unread. A line said outside a tour can wait the same way (`GuideLine.hold`: practice's tips), or be said in passing from the corner (`GuideLine.aside`: a mistake after the first practice). A tour can also be built from live numbers mid-song: lesson 1's practice goes through the first instruction of each kind with the values really in its registers and memory, before and after it runs (`SongWords.closeLook` / `closeLookDone`, started by `PipelineScene.lookClosely`, one at a time), and a step can point at one register's row (`SongTarget` `x3`). A tour plays once: its id goes in `Progress.seenLessons` when it ends (the welcome: `Settings.welcomed`), and in `TAUGHT_IDS` so the cheats can mark it seen. A song tour is keyed by its lesson's id and plays before that lesson's practice (`SongStart.tour`, a list: the memory wall, then the cache), or hands over to another screen (`SongStart.afterTour`: a lesson with no practice).
- How much TICK teaches is the player's choice (`TutorialLevel`: full, short, skip; `TUTORIAL` in `data/tours.ts`, asked as a new game's first job is picked on the board (`TUTORIAL_QUESTION`, `BoardScene.askTutorial`), a row in the settings): ask `teaching()` (`settings.ts`) before playing a tour (`tours`), lesson 1's close looks (`closeLooks`), or practice's tips (`tips`). Every new game starts with the tutorial job, so the question always comes.
- Practice's tips (`Tip` in `song/words.ts`): each is said once a game (`Progress.seenTips`), as its situation reaches the line or its event happens, never because the player is late; so a practice teaches only what's new, and a tip that says something new for another CPU needs its own id. Only the first practice (`SongSetup.guided`: lesson 1's) stops for a mistake; the others say it in passing (`aside`) while the note waits for the right key. BRIEFS plays any lesson whatever the choice. A question from TICK is `guide.ask({ say, choices, done })`; the screen sends it Up / Down (`guide.move`).
- Write for a player who has never heard of a CPU: define each new word the first time it appears (in capitals), with an everyday comparison.
- A step holds up at most one picture or points at one part, in a line of at most 150 characters (`tests/tours.test.ts`); a picture must fit TICK's card (880 × 280 around the middle of the top half).
- Definitions go in `data/glossary.ts`. What a thing on the song screen is goes in `song/words.ts`.

**A setting.** Add it to `Settings` and its default in `settings.ts`, and a row in `SettingsScene`. A setting with several levels keeps them in a table where its numbers live (the difficulty: `DIFFICULTIES` in `rhythm/tempo.ts`), and a setting a song needs reaches it through `SongStart` (`song/setup.ts`), so retries and replays keep it.

## Conventions
- **TypeScript:** only syntax Node can erase (`erasableSyntaxOnly`): no `enum` (use `as const` objects), no `namespace`, no constructor parameter properties (declare the field, assign it in the constructor). Import local files with `.ts`. Type-only imports use `import type`.
- **Comments** say what something is for and why, in plain full sentences, like the code around them; every module opens with a short comment on what it's for. Doc comments on exports.
- **On-screen text:** labels, menus and feedback in capitals; lesson lines and callouts in sentence case; the era's way of naming files comes from `data/menuFiles.ts`. Layout uses 960 x 540 coordinates in every era.
- **Writing (docs and in-game):** plain words, short sentences, no jargon a first-year student wouldn't know without defining it. Companies, products and people in the game are made up; take ideas from other games, never their assets, names or text.
- **Accuracy:** figures follow the textbook; stylized ones (the tempo curve, wear, the overheat limits) are labeled so in lessons and the README.
- **Commits:** build first, so `game/js/` matches `game/src/`. Delete a removed module's compiled `.js` and `.js.map` too (`tsc` doesn't).

## Verifying a change
- Build, both type checks, and the tests, every time.
- Look at it. Headless Chrome works: write throwaway scripts in `.tmp/`; serve `game/` (a few lines of `node:http`); start Chrome with `--headless=new --remote-debugging-port=0 --user-data-dir=.tmp/<name> --disable-breakpad --window-size=1280,720` (read the port from `DevToolsActivePort` in the profile); drive it over the DevTools protocol (`Page.navigate`, `Input.dispatchKeyEvent`, `Page.captureScreenshot`). Set `localStorage` first (`bit-cycler-settings` with `bootSeen: true`, `music: false`; a `bit-cycler-save-1` fixture, whose `wordBits` picks the era), then open `?scene=...` (`&era=N` shows another era) (`&autoplay` plays songs by itself). Shut Chrome with `Browser.close` and wait for it to exit before deleting its profile. Without `--disable-breakpad`, Chrome's crash reporter writes in `~/.config/google-chrome`, outside this directory; even with it, Chrome rewrote `~/.config/google-chrome/Crash Reports/settings.dat` on start (2026-10-31). Starting Chrome with `XDG_CONFIG_HOME` and `CHROME_CONFIG_HOME` set to a folder in `.tmp/` kept that file untouched (2026-11-02): do that every time.
- Compare against the last commit: `git archive HEAD game | tar -x -C .tmp/base` gives the old build to run side by side.
- Playing a screen through by real keys: poll the scene over the DevTools protocol and press Enter while TICK is waiting (`guide.waiting`, once his words are all typed: `guide.words.text.length >= guide.full.length`, then pause over 0.3 s, or the second Enter is ignored), the right lane's key for the instruction in ID otherwise (`run.pipeline.stages.ID`, `run.decided`), Space for a hazard; `cheat.autoplay()` plays real runs. Fixtures: build a save in a small `.tmp/*.ts` from `sim/progress.ts` and `saveFile.ts` (`fillBoard`, `withTier`, `endDay`) and put it in `localStorage` before opening `?scene=...`. Keep `.tmp/` scripts until the checks are done, then empty it (keeping `npm-cache`).
- Headless timing: Phaser's timers and tweens advance per frame and headless Chrome draws few frames, so the boot runs about 5x slow; songs follow the audio clock and run in real time. Never use `--virtual-time-budget` (it freezes `performance.now()`).
- Say what you couldn't check: feel, sound, real-browser behavior.
- `pkill -f` and `pgrep -f` match your own command line too: a pattern that appears in your command kills the shell running it.

## Gotchas already paid for
- **Keys:** Phaser's keyboard plugin re-runs its key queue on every new event (one Enter fired four times), so it's off; all input goes through `input/keys.ts`, judged at the event's own timestamp (`Conductor.beatAt`). Vimium swallows Escape and single letters, so `input/keyFocus.ts` keeps focus on a hidden field, and `Q` works wherever `Esc` does.
- **Scene data:** Phaser restarts a scene with its last data when given none. `Screen.setUp` clears it, so a restart must pass its data again.
- **Scene fields:** a scene is one object reused by every start and restart, so its fields keep their last values (the board came back after clocking out still thinking its timecard was up). Reset every field that `create()` doesn't set in `init()`.
- **Slow frames:** a looping timer can fire several times in one frame (the boot ran twice), so one-shot endings need a guard. Things that must not lag (notes, fades, values on the bus) move on `performance.now()` (the motion player), not Phaser's tweens.
- **Audio in the background:** Phaser suspends the audio clock while the window is hidden, but timers keep going; sounds scheduled then all play at once on return. Cues and the hum's drive skip while `live()` is false.
- **Glow:** Phaser's bloom averages the picture with its blur (halving the letters), so `addGlow` runs it at half strength and doubles the result. The CRT overlay blends as soft light so bright text keeps its brightness.
- **Tweening a rectangle's height** doesn't re-anchor it; scale instead.
- **Floating-point beat times:** compare with tolerances or windows, never `===`.
- **Pausing a song** pauses the `Conductor` (the beat holds, then carries on from where it stopped), not the audio: suspending the `AudioContext` let the beat run on while paused (its output timestamp kept extrapolating), and the song jumped ahead on resuming.
- **JetBrains Mono's ligatures** draw `<-` and `->` as arrows (on purpose in the 64-bit era).
